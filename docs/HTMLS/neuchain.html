1. What it is

NeuChain is a research system from Northeastern University (iDC-NEU), published at VLDB 2022 ("NeuChain: a fast permissioned blockchain system with deterministic ordering", PVLDB Vol. 15). It's written in C++. This benchmark tracks branch ev only — the repository has several architectural variants (eov, oe, oepv) that are out of scope, plus a newer sharded successor, NeuChain+, which is also out of scope. Every claim on this page is specific to the ev branch.

2. The transaction model: ordering-free Execute-Validate

This is the deepest architectural departure of any platform in this benchmark. Every other platform here — Fabric, Drunix, Fabric-X — has a distinct ordering step: some process or set of processes runs a consensus protocol whose specific job is to agree on a sequence of transactions, and only after that agreement happens does validation/commit proceed. NeuChain has no dedicated ordering service at all.

How you get agreement without an ordering step

NeuChain makes ordering implicit through deterministic execution: every node in the network executes the identical set of transactions in the identical logical order, using techniques (asynchronous block generation, execution pipelining, an epoch server for coordination, and block servers that do the actual execution/validation) that guarantee every honest node arrives at the same result without ever needing to run a distinct "vote on the order" round. If every node's execution is a pure, deterministic function of the same inputs processed in the same order, then getting every node to agree on the order is getting every node to agree on the outcome — there's no need to separate those into two steps.

This is a fundamentally different bet than every EOV platform makes. Fabric-family platforms assume execution might be non-deterministic or resource-intensive enough that you want to decide the order cheaply first (via consensus over transaction identifiers or digests) and defer execution until after. NeuChain instead assumes execution can be made cheap and deterministic enough that skipping the separate ordering round entirely is a net win — trading away the ordering step's overhead in exchange for requiring every transaction's execution to be reproducible byte-for-byte across every node.

The direct, disclosed cost of this design: no per-transaction endorsement

The EOV platforms (Fabric, Drunix, Fabric-X) each verify a cryptographic endorsement signature on every single transaction during validation — that's part of what "endorsement policy" means. NeuChain's EV path has no endorsement round at all; there is nothing analogous to endorsement in this design, because there's no separate execution-then-approve step to endorse. This isn't a corner that got cut for performance — it's inherent to what "ordering-free" means. The harness discloses it explicitly and permanently in every NeuChain run's manifest (per_tx_endorsement_verify: false) rather than attempting to "equalize" it by inventing an artificial endorsement step NeuChain doesn't actually have. See the normalization page for why disclosure, not equalization, is the right response to a difference like this.

One nuance worth being precise about: NeuChain does verify the submitting user's RSA signature once, at the moment a block server first receives the transaction (CryptoHelper::getUserSigner(ip)->rsaDecrypt) — it is not running with no cryptographic verification whatsoever. What it lacks is the EOV platforms' per-endorser, per-committer repeated verification during a multi-step validation process. per_tx_endorsement_verify=false is still the correct flag for the cross-platform comparison table, but the manifest's msp_note field carries this nuance in full so nobody misreads the flag as "NeuChain has no cryptographic security at all."

3. How this harness measures it: ZeroMQ, not gRPC

A reasonable assumption going in might be that NeuChain's client protocol is gRPC or Baidu's brpc, since both appear in the codebase. Direct source inspection (a half-day spike against NeuChain commit 5180d5e85ff152eac9c8773378cce84a205080b2) found otherwise: brpc in NeuChain is used exclusively for inter-server communication (block-server-to-epoch-server), never for the client path. The actual client-to-block-server protocol is ZeroMQ + protobuf + RSA-1024/SHA-256 signing — simple enough that the whole client was reimplementable in pure Go with no C bindings at all (no cgo, no linking against NeuChain's own C++ client library).

Submit: a PUB socket, not a request

Submitting a transaction (traced directly from src/user/block_bench/db_user_base.cpp, function sendInvokeRequest):

  1. Build a TransactionPayload (function name, a serialized workload-specific payload, and a random nonce) and serialize it.
  2. Sign that serialized payload with RSA-1024 PKCS#1v1.5 over SHA-256 — this signature, not any separately generated ID, is the transaction's identifier used to track it through to finality.
  3. Wrap payload and signature into a UserRequest and serialize it.
  4. Publish that serialized message on a ZeroMQ PUB socket, addressed to every block server at once (a direct consequence of deterministic execution: every node needs the same input, so the client fans it out to all of them itself rather than relying on a leader to relay it).
Why "T2" is not a meaningful concept for NeuChain's submit path

ZeroMQ's PUB socket type is fire-and-forget by design — there is no reply, no acknowledgement frame, nothing that comes back over the wire at all. The only event a client-side adapter can observe at "submit time" is its own local send() call returning, which reflects how fast the client's own network stack accepted a local write into its outbound buffer — it says nothing whatsoever about whether any block server has received, let alone processed, the transaction. Reporting that as a "T2 acknowledgement" comparable to Fabric's real orderer-accept event would be actively misleading, in the same structural way Fabric-X's blocking REST call makes its T2 non-existent (see the Fabric-X page) — two completely different root causes (fire-and-forget vs. synchronous-to-finality) producing the same practical conclusion: no real T2 to report.

Finality: polled, not pushed

Since nothing is pushed back to the client, finality has to be actively polled, over a separate ZeroMQ REQ socket to a block server's query port:

Query typePayloadReply
tip_query(empty)latest committed block height, as a bare ASCII integer
block_queryblock number as a stringthe full serialized block

The polling algorithm: repeatedly ask tip_query for the current height; whenever it advances, fetch the new block(s) with block_query, then scan every transaction entry inside for one whose embedded digest matches a signature this client is still waiting on. When found, decode that entry's result frame (below) to learn whether it committed or aborted. T3 is the moment this match is found and decoded — a real, well-defined finality event, just reached by polling rather than by the platform notifying the client directly.

The result frame is hand-rolled, not protobuf

Somewhat surprisingly given how much of the rest of the protocol is protobuf, each transaction's result entry inside a queried block is a hand-rolled binary format, not a protobuf message:

uvarint tid
uvarint epoch
uvarint digestLen
bytes   digest       # matches the UserRequest.digest sent at submit time
uvarint result       # 0=COMMIT, 1=PENDING, 2=ABORT, 3=ABORT_NO_RETRY

The Go adapter decodes exactly this 5-field frame using encoding/binary.Uvarint — it does not need NeuChain's richer full-transaction frame (which additionally carries the original payload, a read/write set, and a trailing hash), because the client only ever needs to know whether its own submitted transaction committed or aborted, not to re-derive the transaction's contents from the block.

4. Mapping the normalized workload onto NeuChain's native call shape

NeuChain's chaincode-equivalent primitive is a YCSB_PAYLOAD (table name, a list of keys read, a list of keys updated) passed as the payload of a named function call. The normalized TxKind values map onto it directly:

Harness TxKindreadsupdate
TxWrite—[key]
TxRead[key]—
TxTransfer[src, dst][src, dst]

One caveat worth being explicit about: the actual function name and table name invoked come from NeuChain's own deployed chaincode configuration, not from the normalized workload definition itself — this is the one place where the "same logical effect, native implementation" principle has to lean on a NeuChain-side config value rather than something the harness fully controls, and it's recorded as a manifest caveat accordingly. Similarly, if the deployed chaincode doesn't expose a native two-account read-modify-write, the adapter composes a transfer from two separate KV operations inside one deterministic transaction — also a recorded caveat, not a silent substitution.

5. What is deliberately not reimplemented

Each of these is a conscious simplification, recorded as a manifest caveat on every NeuChain run rather than silently assumed:

  • Single logical user. NeuChain supports a multi-proxy mode with a separate keypair per block-server IP; this adapter uses one keypair for all servers, which is a reasonable simplification for a benchmark client but not how a production multi-tenant deployment would necessarily be configured.
  • No client-side MVCC awareness. The adapter submits and waits; all conflict resolution happens server-side via deterministic execution, and surfaces to the client only as a plain result == ABORT, with no detail about what conflicted.
  • RSA-1024. Weak by current cryptographic standards, but it's what NeuChain's own ev branch verifies (RSA_KEY_LENGTH is fixed at 1024 in the source) — the adapter matches the platform rather than silently "upgrading" it, since the point is to benchmark NeuChain as it actually behaves. Recorded plainly in CryptoInfo.
  • Empty private-key password. NeuChain's own key-generation utility uses an empty passphrase by default; if a real deployment sets one, the adapter would need that passphrase supplied via config.
  • Query load from polling. The tip_query/block_query polling loop itself adds request load on the block server's query port. At very high block rates the poller can lag behind; this shows up as growing finality latency in the results, not as lost transactions — a distinction worth knowing when reading a NeuChain latency curve that grows unexpectedly at the top end of a sweep.

6. Local-run scale caveat

Like Fabric-X's Arma, NeuChain is built for high core counts, and the published VLDB numbers reflect cluster-scale hardware. Run locally (4 block servers plus 1 epoch server sharing roughly 6 cores, in this benchmark's default profile), it performs well below its paper numbers for the same structural reason Fabric-X does — not enough independent hardware to exploit the pipeline parallelism the design assumes. Every local NeuChain run automatically carries this caveat; quotable, paper-comparable numbers require the gcp-full profile.

7. Where this stands today

Done and unit-tested, pure Go

The full client-side implementation exists and is unit-tested: RSA-1024/SHA-256 sign-then-verify round-trip, the hand-rolled result-frame decoder (including truncated-frame error handling), and the shape of a built invoke request (correct digest, correct read/update sets for a transfer, correct nonce encoding). No live NeuChain network was needed to verify any of this — it's pure protocol-level correctness against the documented wire format.

Compute-gated: the server binaries don't exist yet

NeuChain's own server (block_server, epoch_server) has to be compiled from source, and that build compiles roughly 15 pinned C++ libraries from scratch (protobuf via autotools, brpc, braft, and others) on Ubuntu 20.04 with a specific gcc/cmake toolchain. Measured cold-build time is 45–90 minutes, needs 25–30 GB of free disk for the build image and intermediate objects, and RAM spikes to 6–10 GB during parallel compilation of the heaviest libraries — enough to risk an out-of-memory kill on a modest host if run alongside anything else. None of this reflects a problem with the adapter; it's simply a multi-hour, resource-heavy compute job that has to run to completion before there's a live NeuChain node for the already-finished adapter to talk to.

The pluggable entry point once compute is available: bash deploy/docker/neuchain/build.sh, followed by the pre-initialized-database and keypair-generation steps documented in docs/REMAINING-WORK.md §1. Once the server images exist, deploy/docker/neuchain/up.sh local brings the topology up and the existing adapter runs against it with no code changes.
