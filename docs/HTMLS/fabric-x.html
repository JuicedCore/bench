1. What it is

Fabric-X (LF Decentralized Trust) is not a fork or a variant of Fabric — it is a ground-up re-architecture that decomposes the monolithic Fabric peer into independently scalable microservices (endorser, validator, committer) and replaces the Raft/SmartBFT orderer entirely with Arma, a sharded BFT ordering service. Its published evaluation reports throughput above 200,000 TPS on a large cluster (a CBDC benchmark). Of the four platforms in this benchmark, Fabric-X is the one furthest from Fabric's original design, on two independent axes at once: how consensus works, and what a transaction even is.

2. No chaincode: a different transaction model, not just a different consensus

This is the single most important thing to understand about Fabric-X, and it's easy to under-appreciate: Fabric-X does not run chaincode at all. There is no PutState/GetState, no deployable smart contract, nothing to install or approve. In its place, transactions are negotiated peer-to-peer through Fabric-Smart-Client (FSC) views and sessions, built on top of the Fabric-Token-SDK — a UTXO (unspent transaction output) model, the same conceptual family as Bitcoin's ledger, not an account-balance model.

UTXO vs. account/KV, concretely

On Fabric, Drunix, or NeuChain, a transfer is a read-modify-write: read account A's balance, read account B's balance, write both back updated. On Fabric-X, a transfer consumes existing unspent token outputs belonging to the sender and creates new outputs assigned to the recipient (plus, in a full implementation, a change output back to the sender) — nothing is ever overwritten in place. This changes what "the same transaction" even means across platforms, and is exactly why the harness defines workloads by logical effect rather than by wire format — see the normalization page.

The direct consequence: the exact same smart-contract bytecode cannot be deployed across all four platforms in this benchmark, because Fabric-X has nowhere to deploy it to. The harness's answer is to define each normalized workload as a logical effect and implement it natively per platform — for Fabric-X, that means routing through FSC views and the Token SDK instead of chaincode invocations.

3. Arma: sharded ordering by digest, not by payload

Arma replaces the single-leader-or-BFT-quorum orderer model with four distinct server roles working as a pipeline:

  • Routers — accept incoming transactions from clients and dispatch them onward.
  • Batchers — group transactions into batches.
  • Consenters — run BFT agreement over compact digests of each batch, not the full transaction payloads themselves.
  • Assemblers — reconstruct full, ordered blocks from the agreed-upon digests plus the batch data held by the batchers.

Ordering digests instead of full payloads is specifically where Arma's throughput advantage comes from: the expensive BFT agreement step only ever moves small, fixed-size digests across the network, regardless of how large the underlying transactions are, while the bulk transaction data moves separately and can be pipelined. This is a genuinely different scaling strategy than SmartBFT's approach of running BFT agreement directly over the transaction batch.

4. How this harness measures it — and where the T1/T2/T3 timeline breaks down

The real Fabric-X REST API (verified directly against fabric-x-samples/tokens/swagger.yaml) is token-only, with no KV route at all:

Every write route runs ttx.NewOrderingAndFinalityView(tx) internally before the HTTP response is returned — confirmed directly in the sample's own source (tokens/owner/service/fsc.go). This is not a client-library quirk or a timeout misconfiguration; it's how the API is built. The POST call blocks until the transaction is already ordered and final, and only then sends back a response.

Why Fabric-X genuinely has no T2

Recall from the normalization page that T2 is meant to capture "the platform acknowledged receipt, before finality." On Fabric, that's the orderer accepting a broadcast — a real, separate event. On Fabric-X, there simply is no earlier point to observe: by the time the POST call returns at all, ordering and finality have already happened. Asking "what was the submit-ack latency" is not a question this API can answer, in the same way you can't ask a synchronous function call what its "acknowledgement time" was separately from its return time — there's only one event to observe, not two. This is a structural property of the API, not a gap in the adapter.

The adapter (pkg/adapters/fabricx) works around the blocking call as gracefully as the situation allows: Submit fires the POST in a background goroutine and returns immediately with AckTime = now — explicitly marked advisory, not a real measurement — while WaitForFinality blocks on that same goroutine and reports its completion as T3. T1 (generator-side, before submit) and T3 (the POST actually completing) are both real and comparable to every other platform. Submit latency and commit latency, individually, are reported as N/A for Fabric-X in every comparison table — not zero, not omitted silently, but explicitly flagged as not applicable, so a reader never mistakes "no data" for "instant."

5. The custom KV view: filling a gap the real API doesn't have

Because the normalized kv-write/kv-read/kv-mixed workloads need some key-value primitive to drive, and Fabric-X's real, published API has no KV route whatsoever, the harness adds one: a custom FSC view service at deploy/docker/fabricx/kvview/ exposing a plain POST /kv endpoint that does key/value writes and reads over the same FSC session mechanism the token routes use.

This is honestly disclosed as a mismatch, not presented as native

The KV view is a view/session round-trip built specifically for this benchmark — it is not a native Fabric-X primitive, it carries FSC negotiation overhead that has no equivalent step on Fabric, Drunix, or NeuChain, and it inherits the same synchronous-to-finality behavior as the token routes (so it has no T2 either). Every run using it carries an explicit caveat: "Fabric-X KV via a custom FSC view — not a native Fabric-X primitive; the FSC node + HTTP server are in the measured path and have no equivalent on Fabric/Drunix/NeuChain. Submit latency is N/A. Compare E2E latency and TPS trends only." See the normalization page, Section 5 for the general policy this follows: run it anyway, caveat it loudly, never silently drop the data point.

The KV view is currently a compiling stub — POST /kv returns HTTP 501 — with a full code-level implementation spec written up in its own README.md, confirmed against the real fabric-smart-client@v0.20.0 API for registering FSC write/read views. Finishing it requires a live Fabric-X devnet to build and iterate against (the FSC node has to join a real network before its views can be tested), which is why it's grouped with the other devnet/compute-gated work rather than something completable without infrastructure. Token workloads (issue/transfer/redeem) work today and don't depend on this at all.

6. Local-run scale caveat

Arma and the Fabric-X committer stack are explicitly scale-out designs — the published 200,000+ TPS figure comes from a large multi-node cluster. Run locally (roughly 8 cores shared across all Fabric-X services on this benchmark's default profile), throughput sits far below that published ceiling, for reasons that have nothing to do with Arma's design being slow and everything to do with there simply not being enough independent hardware to shard across. Every local Fabric-X run automatically carries a manifest caveat stating that absolute TPS is not comparable to the ~200k figure. What does remain informative locally is the shape of the latency curve as offered load increases, and relative behavior under contention — those characteristics of Arma's design don't require cluster scale to observe, even though the absolute ceiling does. Full-scale, publication-comparable numbers require the gcp-full resource profile.

7. Deploying it

deploy/docker/fabricx/up.sh runs the whole devnet bring-up:

  1. Clones hyperledger/fabric-x-samples.
  2. Runs tokens/ make setup && make start — brings up the Arma ordering service, the committer stack, and issuer/endorser1/owner1/owner2 services (ports 9100/9300/9500/9600).
  3. Calls POST /endorser/init to commit the token parameters that the network needs before any transaction can run.
  4. Builds and starts the kvview service (bench/fabricx-rest, port 9700) on the shared fabric_test Docker network.
  5. Emits connection.env (BENCH_ADAPTER_OWNER_URL and friends) for the benchrunner CLI to pick up.

down.sh runs tokens/ make teardown followed by docker compose down.

8. Where this stands today

Working today

The adapter matches the verified real fabric-x-samples/tokens API and is httptest-tested against real route shapes (transfer, KV write/read, an unreachable-service case, and the submit-returns-before-finality behavior). Token transfer workloads run live against a real devnet today.

Gated on a live devnet

Normalized kv-* workloads need the custom KV view finished, which needs an already-running Fabric-X devnet to iterate against — grouped with other infrastructure-dependent work, not a code gap on this benchmark's side.
