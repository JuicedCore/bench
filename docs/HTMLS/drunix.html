1. What it is

Drunix is an enhanced fork of Hyperledger Fabric 2.5.x, open-sourced by NPCI (National Payments Corporation of India) in mid-2026, aimed at tokenization workloads and large multi-organization networks. Critically, it keeps the standard Fabric Gateway SDK's API surface — existing Fabric client code is meant to work against it unchanged. That compatibility promise is exactly what this benchmark tests, and exactly where it currently breaks (Section 5).

2. The transaction model: same EOV shape, restructured peer

Drunix does not change Fabric's fundamental Execute-Order-Validate model — a client still endorses, then orders, then validates and commits. What it changes is who performs each of those steps inside what used to be one monolithic peer process:

ChangeEffect
Peer split — Lite Peer (endorsement only) + Committing Peer (validation + commit)Endorsement throughput and commit throughput can now scale independently of each other — you can add more Lite Peers without touching the commit path, or vice versa.
Stateless Validation ServiceMVCC/VSCC validation work is offloaded from the Committing Peer into a separate, horizontally-scalable service.
YugabyteDB (SQL) state optionAlongside LevelDB and CouchDB, world state can live in a relational store — enabling SQL queries over ledger state, which the shipped default configuration uses.

This is a meaningful architectural bet: stock Fabric's peer does endorsement, validation, and commit all in one process, so scaling any one of those means scaling all of them together. Drunix's disaggregation is trying to remove that coupling. Whether it actually delivers better throughput at scale is exactly the kind of question this benchmark exists to answer — but answering it honestly requires first understanding that the split changes where in the pipeline a client needs to look to find out "is my transaction done," which is the crux of Section 4 below.

Consensus: CFT only

Drunix inherits Fabric 2.5.x's Raft orderer wholesale — there is no BFT ordering path at all. This is a real scope limitation, not a benchmark gap: Drunix simply cannot be run in a Byzantine-fault-tolerant configuration. Because of this, Drunix only appears in CFT comparisons, set directly against fabric-cft (both Raft, both crash-fault-tolerant). It is deliberately excluded from the stronger-ordering comparison group that includes Fabric SmartBFT, Fabric-X's Arma, and NeuChain's deterministic consensus — putting a CFT-only platform in a BFT comparison would be comparing systems with fundamentally different fault-tolerance guarantees as if throughput were the only thing that mattered.

3. How this harness measures it

The Drunix adapter (pkg/adapters/drunix) is a thin wrapper over the Fabric adapter — it reuses the identical Gateway SDK flow (Endorse → Submit → Commit.Status) and the identical T1/T2/T3 definitions described on the Fabric page. This is possible precisely because Drunix preserves the Gateway SDK's API surface. What differs is where the adapter points that SDK:

  • endorse_endpoint targets the Lite Peer — the Gateway SDK opens its one connection here, since this is the node that runs endorsement and hosts the gateway service.
  • commit_endpoint documents the Committing Peer — but the Gateway SDK does not talk to it directly for the standard commit-status call, for the reason below.

Why finality has to be read differently here than on stock Fabric

On stock Fabric, the peer that endorses is generally also able to tell you when a transaction commits (Commit.Status() on the Gateway just works). On Drunix, endorsement and commit are two different processes on two different peers by design — and the Lite Peer, which is where the Gateway lives, never commits anything itself. That means Commit.Status() on the Lite-Peer-hosted Gateway simply never fires; there's nothing wrong with the call, it's asking the wrong node a question it structurally cannot answer.

The adapter's fix: set UseCommitPeerEvents=true (implemented in pkg/adapters/fabric/commitpeer.go), which opens a second Gateway connection — this one to the Committing Peer directly (port :7061, same shared TLS CA, with SNI peer1.org1.example.com) — and reads transaction validation results from that peer's FilteredBlockEvents stream instead. This is a genuinely different signal path than any other platform in this benchmark uses: it's still watching for a block-commit event, so T3 still means the same thing conceptually, but the client needs two live connections to two different services to observe the full T1→T2→T3 lifecycle, where Fabric-proper needs one.

Why this doesn't compromise comparability

T3 is still "the adapter observed this transaction committed in a validated block" — the same definition used everywhere else. Watching a different peer's event stream to observe that fact doesn't change what's being measured, only how the measurement is wired up. This is different in kind from Fabric-X's situation (next page), where the platform's own API makes a genuine T2 impossible to observe at all.

4. Known blocker: vanilla writes panic the Committing Peer

Application writes do not currently complete on Drunix

Every write transaction submitted through the stock hyperledger/fabric-gateway SDK reaches the orderer successfully, but the Committing Peer panics on commit. Across a live test run: submitted 1101, errored 0, timed_out 1101 — every single write endorsed and broadcast correctly, and every single one then failed to reach finality because the peer that was supposed to commit it crashed first.

[orderer] WARN [common.sparseblock] aggregateOrgEnvelope -> txnEnv.LeanEnv is nil it could be vanilla-format txn   (x hundreds)
[cp.org1] panic  github.com/npci/drunix/core/ledger/kvledger.(*kvLedger).commit
                 github.com/npci/drunix/gossip/privdata.(*coordinator).StoreBlock
                 github.com/npci/drunix/gossip/state.(*GossipStateProviderImpl).commitBlock

The technical root cause, explained

Drunix advertises a "sparse block" optimization intended to reduce the amount of data peers exchange over gossip. To make that optimization work, it expects transactions to arrive in a Drunix-specific lean envelope format (txnEnv.LeanEnv) rather than the standard Fabric transaction envelope. The stock Fabric Gateway SDK — the one every Fabric client, including this benchmark's adapter, actually uses — has no concept of a lean envelope; it only ever produces vanilla Fabric envelopes, because that's the only format the public Fabric protocol defines. When the Committing Peer's aggregateOrgEnvelope function receives one of these vanilla envelopes and tries to unwrap it as if it were a lean envelope, the field it expects to find (LeanEnv) is simply absent, and the commit path panics rather than falling back gracefully.

In plain terms: Drunix quietly changed the format transactions need to arrive in to get the performance benefit of its sparse-block design, but never shipped a client that produces that format, and its server-side code doesn't recognize (and gracefully reject or accept) the old format — it crashes instead. Since the standard SDK is the only thing that exists to talk to a Fabric-compatible gateway, there is currently no way to submit an application write to Drunix that this benchmark (or any standard Fabric client) can reach.

What still works despite this

Critically, this is not a broken deployment — it's a narrow, specific gap. Read-only Query calls (Evaluate, no ordering/commit involved) work correctly, and the entire chaincode lifecycle (package, install, approve, commit the chaincode definition itself — which also uses vanilla envelopes) was verified working end to end: 7 npcioss/drunix-* containers running (Lite Peer / Committing Peer / stateless VSCC across 2 orgs, plus a Raft orderer), 2 KeyDB containers, YugabyteDB, a channel joined, blocks committing, and the kvstore chaincode packaged, installed, approved, and committed as VALID on both Committing Peers. Only the application-write data path — the actual normalized-workload transactions this benchmark needs to measure throughput — is blocked.

What resolves it

This needs one of three things from the Drunix side, none of which this benchmark can supply on its own:

  1. A Drunix-aware client SDK (or a Drunix-patched fabric-gateway) that actually emits lean-envelope-format transactions. The public npci/drunix repository currently ships only chaincode samples and the CLI-driven network.sh — no client SDK exists yet.
  2. A server-side fix so aggregateOrgEnvelope/kvledger.commit falls back cleanly to handling vanilla envelopes instead of panicking on them.
  3. Official documentation of a supported deployment mode that accepts vanilla-SDK writes (possibly by disabling the sparse-block optimization outright).

Everything on this benchmark's side is already built and waiting: the Committing-Peer event-stream finality path described in Section 3 is implemented and passes build/vet checks — it simply has nothing to resolve, because the Committing Peer never gets far enough to commit. Once any of the three fixes above lands upstream, the Drunix adapter should work with no further changes on this side.

5. State database: Yugabyte by default, LevelDB by patch

Drunix's shipped Docker Compose configuration hardcodes YugabyteDB as the state database (CORE_LEDGER_STATE_STATEDATABASE=sqldb plus the Yugabyte connection environment) — there is no ready-made LevelDB or CouchDB compose variant. But this benchmark's normalized runs require LevelDB everywhere for fairness (see the normalization page), so up.sh patches the compose file for normalized runs: it rewrites sqldb to goleveldb and strips the SQL connection settings, so the peer falls back to LevelDB from its default core.yaml. down.sh restores the original file from a backup. Platform-native Drunix runs (measuring Drunix at its own best, not in a cross-platform comparison) keep Yugabyte and record that choice in the run manifest.

6. Fairness levers

Identical to Fabric for every normalized run: LevelDB (forced, as above), the same orderer batch parameters (shared anchor values in deploy/profiles/*.yaml), and the same crypto (ECDSA P-256/SHA-256, per-transaction endorsement verification, reported as Fabric's CryptoInfo with a Drunix note attached). The Lite-Peer/Committing-Peer split and the Validation Service are architectural, not tuning knobs — they stay on for every single Drunix run, because they are exactly the design this comparison is trying to measure. Turning them off to "simplify" the comparison would mean no longer benchmarking Drunix at all.

8. Where this stands today

Verified live

Full deploy, channel join, chaincode lifecycle (package/install/approve/commit), and Committing-Peer finality-event wiring all confirmed working end to end against a live network.

Blocked upstream

Application write throughput/latency cannot currently be measured — every write endorses and orders successfully but times out waiting for a commit that never happens, for the reason in Section 4. This is tracked as a genuine third category of open work (distinct from "needs more compute" or "needs cloud credentials") — it needs a fix from the Drunix project itself.
