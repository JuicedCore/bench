Bench Overview Fabric Drunix Fabric-X NeuChain Normalization

How we make four incompatible platforms "do the same thing" The normalization methodology behind every cross-platform number in this benchmark

The problem in one sentence

Fabric runs chaincode. Fabric-X has no chaincode at all — it moves UTXO-style tokens through a view/session protocol. NeuChain has no ordering service. You cannot point the same script at all three and expect it to submit "the same transaction," because there is no such thing as a transaction shape that is native to all three at once.

1. Why "just run the same code everywhere" doesn't work

Every one of these platforms is a permissioned ledger, and every one of them ends up with the same effect if you squint — some piece of state changes, and eventually everyone agrees it changed. But the path to that agreement is architecturally different in ways that go deeper than configuration:

ModelPlatformsShape
Execute‑Order‑Validate (EOV) with chaincodeFabric (CFT + BFT), DrunixClient → endorse (execute) → order → validate → commit
Execute‑Order‑Validate without chaincodeFabric‑XFSC view/session negotiation + Token SDK (UTXO), Arma sharded ordering
Ordering‑free Execute‑Validate (EV)NeuChainDeterministic execution — no dedicated ordering step at all

A benchmark tool that submits "a chaincode invoke" simply has nowhere to send that invocation on Fabric-X (there's no chaincode container to receive it) or on NeuChain (there's no chaincode execution model — it runs a fixed, deterministic function set). Conversely, a tool that drives each platform through its own bespoke client can't produce comparable numbers, because "fast on platform A's own benchmark tool" and "fast on platform B's own benchmark tool" tells you nothing about which platform is actually faster under the same conditions — the tools themselves might differ by more than the platforms do.

The way out is not to force one wire format onto all four platforms. It's to define what "the same transaction" means at a logical level, and let each platform satisfy that logical contract using whatever primitive is native to it.

2. The normalized workload: one contract, four implementations

This is the actual definition used across the whole harness (pkg/workloads/workload.go). "Equivalent" here does not mean identical bytes on the wire — that's provably impossible across three transaction models. It means three things hold simultaneously:

  1. The same logical state effect. "Set this key to this value" or "move this amount from account A to account B" — not "call this specific function with this specific payload format."
  2. The same key-selection process. One deterministic, seeded generator decides which keys are touched, in what order, under what contention pattern (uniform / zipfian / fixed) — identical across all four platforms for a given run.
  3. Measured at the same two points in time. Not the same wire message, but the same two conceptual moments: "the platform has acknowledged this" and "the platform has finalized this." (Section 3 below explains why even this needs care.)
Normalized workloadWhat it meansFabric / DrunixFabric‑XNeuChain
kv-writeSet one keychaincode Put(key,value)custom FSC KV-write viewnative KV write RPC
kv-readRead one keychaincode Get(key) (Evaluate)FSC read viewnative KV read RPC
kv-mixedRead/write blend by ratioGet / Putread / write viewread / write RPC
transferMove value between two accountschaincode Transfer(from,to,amount) (read-modify-write two accounts)Token SDK Transfer (native) or FSC transfer view (normalized)native transfer RPC

Each row is implemented once as a stream of abstract adapters.Transaction values, and then translated into whatever that specific platform actually understands. The translation layer is a PlatformAdapter — the harness never special-cases a platform inside the load generator or the metrics collector; all platform-specific knowledge lives behind one narrow interface (Setup / Submit / WaitForFinality / Query).

Why this is fair and not just "close enough"

The alternative to normalization isn't a more perfect comparison — it's an impossible one, or a meaningless one. Since Fabric-X has no PutState, insisting on byte-identical wire behavior would mean simply never benchmarking Fabric-X's KV performance at all. Normalizing at the logical-effect level is what makes a same-key, same-contention, same-measurement-window comparison possible in the first place.

3. The real trick: one timeline, even when a platform can't natively produce all of it

Every transaction on every platform is measured against the same three-point timeline:

scheduledwhen the load generator intended to send it
T1captured right before adapter.Submit — identical code path for every platform
T2the platform acknowledges receipt
T3the adapter observes it committed in a finalized block

T1 is easy — it's generator-side, so it's trivially identical across platforms. T3 is also well-defined everywhere: every one of these systems eventually produces a finalized, ordered block (or, for NeuChain, a deterministically-agreed execution result), and "I saw my transaction land there" is a real, comparable event on all four. Throughput and headline latency are always computed from T3, never from T1 — reporting only submit-to-ack latency, as some blockchain benchmarks do, silently discards the entire cost of ordering, validation, and commit.

T2 is where the four platforms genuinely stop being comparable, and this is the crux of the whole normalization exercise. It's not a measurement bug to be fixed — it's a real difference in what each platform's client protocol makes observable, and pretending otherwise would produce numbers that look comparable but aren't.

Why T2 means something different everywhere — and where it means nothing at all

PlatformWhat T2 actually isIs it a real, separate measurement?
Fabric / DrunixThe orderer accepts the broadcast envelope (Gateway SDK's Submit returns)yes Endorsement happens client-side before this point, ordering happens after — two genuinely separate network round-trips with independent costs.
Fabric‑XN/A — the REST call blocks until finalityno There is no moment where the platform says "received, will get back to you" — the HTTP POST simply doesn't return until the transaction is already final. T2 is not missing because nobody built it; it structurally cannot exist over this API.
NeuChainThe instant the client's ZeroMQ PUB socket's send() call returnsno PUB is fire-and-forget — there is no reply, no acknowledgement frame, nothing from the network at all. A "T2" here is measuring how fast the client's own network stack accepted a local write, not anything the NeuChain platform did.

This has a very concrete, very easy-to-miss consequence for reading any report this harness produces: a "submit latency" column that shows numbers for Fabric-cft and Fabric-X side by side is not comparing two measurements of the same thing. Fabric's number reflects real endorsement-and-broadcast network cost. Fabric-X's and NeuChain's numbers, if reported at all, would reflect essentially nothing — a REST client library returning after synchronous work, or a local syscall returning immediately. Because of this, the harness does not print a submit/commit split for Fabric-X or NeuChain at all; it reports those columns as N/A rather than a number that looks legitimate but isn't. See the comparable-metrics table below for the exact rule.

Rule of thumb when reading any result

If a metric can be produced by every platform's own client-observable network behavior, it's comparable. If producing it for one platform would mean measuring something structurally different from what it measures on another (a REST library's internal buffering vs. a real consensus round-trip), it is reported as N/A rather than as a misleadingly precise number.

Deliberately not compared: each platform's own metrics

Endorsement time, ordering time, validation-phase breakdown, mempool depth — every platform exposes some of its own /metrics, and every one of those numbers means something platform-specific. They're captured (stored as native_scrapes in each run's result.json) purely to help explain why a platform behaved a certain way after the fact. They never appear in a cross-platform comparison table — mixing "Fabric's self-reported endorsement time" against "NeuChain's self-reported execution time" would compare two numbers that were never measured the same way even in principle.

Held identical for every normalized run

These are the "fairness levers" — things that could vary and would then confound the comparison, so they're pinned to one value across every platform in a comparison run:

Disclosed, never "equalized": cryptography

The EOV platforms (Fabric, Drunix, Fabric-X) verify an endorsement signature on every single transaction during validation. NeuChain's EV path has no endorsement round at all — a transaction is verified once, at submit time, by whichever block server receives it, and that's the only signature check it ever gets. This is not a bug or a shortcut in the harness; it is a real architectural difference between deterministic-execution consensus and endorsement-based consensus. Rather than trying to "equalize" it (which would mean either weakening Fabric's security model or bolting an artificial endorsement step onto NeuChain that it doesn't actually have), the harness discloses it plainly in every run's manifest:

signature_alg:             (e.g. ECDSA-P256-SHA256, or RSA-1024-PKCS1v15)
hash_alg:                  SHA-256 everywhere
per_tx_endorsement_verify: true (Fabric/Drunix/Fabric-X) | false (NeuChain)
msp_note:                  free-text explanation of what verification actually happens

Every comparison table footnotes this next to the throughput numbers — a platform that skips per-tx endorsement verification has a structural advantage on raw TPS that has nothing to do with how good its ordering layer is, and a reader should be able to see that in the same glance as the number.

5. Where normalization gets awkward, and what happens then

Not every platform maps cleanly onto every normalized workload. When it doesn't, the policy (see the platform pages for specifics) is: run it anyway, and attach an explicit, readable caveat — never silently skip the data point, because a missing number is itself misleading (it looks like "we forgot" rather than "here's why this isn't a fair fight").

  • Fabric-X + kv-write/kv-read/kv-mixed — Fabric-X has no KV route at all in its real API, so the harness runs a purpose-built FSC view service that adds one. That service is not a native Fabric-X primitive, it carries FSC negotiation overhead none of the other platforms pay, and — like the token routes — it's synchronous to finality, so it inherits the "no T2" caveat too. Full detail: the Fabric-X page.
  • Fabric-X + transfer — this one is native (Token SDK Transfer), but the normalized version pins it to a plain amount-1 transfer between two fixed accounts, not a realistic multi-denomination UTXO flow with coin selection and change outputs. That richer behavior only shows up in Fabric-X's platform-native runs.
  • NeuChain + transfer — if NeuChain's deployed chaincode config doesn't expose a native two-account read-modify-write, the adapter composes it from two KV operations inside one deterministic transaction. Any such composition is recorded as a manifest caveat.
  • Fabric-X / NeuChain on the local resource profile — not a workload mismatch but a scale mismatch: both are scale-out designs (Arma's sharded ordering, NeuChain's multi-block-server pipeline) benchmarked here on roughly 6–8 cores instead of the cluster hardware their published numbers assume. Every local run of these two platforms carries an automatic caveat that absolute TPS is not comparable to their published ceilings — only the shape of the latency curve and relative behavior under contention are informative locally.

6. Two kinds of run, never mixed

Alongside the normalized comparison, each platform also runs its own platform-native workload — tuned to that platform's actual strengths (its preferred state DB, its own batch tuning, its own best-fit transaction shape). This answers a genuinely different question: not "how do these four compare on identical work" but "what can each one do when you let it play to its strengths."

Native and normalized results are reported in separate sections and never appear in the same comparison table — mixing them would silently compare "platform A under identical constraints" against "platform B tuned to its own advantage," which defeats the entire point of normalizing in the first place.

7. What actually changes across the transaction models — UTXO vs. account/KV

The sharpest data-model divergence in this whole comparison is Fabric-X. Fabric, Drunix, and NeuChain are all, at bottom, key-value/account-style state models: a transfer reads two account balances and writes two new ones in place. Fabric-X's Token SDK is UTXO-based: a transfer consumes existing unspent outputs and creates new ones — nothing is overwritten in place, ever.

This matters for reading throughput numbers honestly. A UTXO transfer's validation cost scales differently than a read-modify-write's — it depends on how many outputs need to be consumed and how large the resulting output set grows, not on lock contention over two fixed keys. If Fabric-X shows different throughput behavior under contention than the account-model platforms, that could be telling you something about Arma's ordering speed — or it could simply be an artifact of the two models having fundamentally different state-growth and conflict-detection costs that have nothing to do with consensus at all. The harness doesn't attempt to erase this difference (it can't — it's not a tuning knob, it's what the platform is); it just makes sure the difference is named so nobody mistakes a data-model effect for a consensus-speed effect.

The one-paragraph version

Every platform is driven through the same abstract workload definitions, the same key-selection process, and the same T1/T2/T3 timeline. Where a platform's protocol can't produce a genuine T2, the harness reports N/A instead of a fabricated number. Where an architectural difference (crypto, UTXO vs. KV, resource scale) would make a raw number misleading on its own, it's disclosed next to the number rather than smoothed away. That combination — identical measurement code, honest gaps where a platform genuinely can't be measured the same way, and disclosed rather than hidden architectural differences — is what "fair" means in this benchmark.
