1. What it is

Fabric is a permissioned EOV ledger: clients endorse proposals on peers, an orderer batches envelopes into blocks, then peers validate (VSCC + MVCC) and commit. It optimizes for flexible endorsement policy and auditability more than raw TPS.

2. Execute-Order-Validate

client ──proposal──▶ endorsing peers (simulate chaincode, sign RW-set) ◀─endorsements─ client ──envelope──▶ orderer (Raft / SmartBFT) ── T2 ≈ orderer accept orderer ──block──▶ peers peers: VSCC + MVCC + commit ── T3

Execution happens before global order, so two valid endorsements can still collide at commit (MVCC). Invalid txs land in the block with Valid=false — the harness does not count them as throughput.

3. How the harness measures it

Adapter pkg/adapters/fabric uses the fine-grained Gateway path — NewProposal → Endorse → Submit — plus a filtered-block / commit listener for finality. It does not use one-shot SubmitTransaction (that would merge T2 and T3).

  • kv-write — Put(key, value) → PutState. Blind write; almost no MVCC.
  • kv-read — Evaluate("Get") on one peer. No orderer. Finality immediate.
  • transfer — chaincode RMW of two account balances (real MVCC under Zipfian contention).

Chaincode: chaincodes/kvstore — deliberately trivial so cost is the platform path.

4. CFT vs BFT

VariantFabricOrdererLocal topologyFault model
fabric-cft2.5.x (e.g. 2.5.16)Raft2 peers, 1 orderer, 2 CCCrash-fault tolerant
fabric-bft3.1.x (e.g. 3.1.5)SmartBFT2 peers, 4 orderers, 2 CCByzantine (3f+1)

Same client port :7051; mutually exclusive on one host. BFT spreads the profile memory budget thinner — the usual OOM risk under probe-sweep.
