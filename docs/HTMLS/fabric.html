Hyperledger Fabric live-tested CFT (Raft) and BFT (SmartBFT) variants — the baseline platform for every comparison in this benchmark

1. What it is, in plain terms

Fabric is built for enterprise consortium ledgers: a known, permissioned set of participants, modular trust between organizations, a rich general-purpose data model, and a pluggable consensus layer. It optimizes for flexibility and auditability, not raw transactions-per-second — typical tuned throughput is a few thousand TPS, and the architecture deliberately trades some latency for endorsement-based programmability (any organization can require its own peers to independently re-execute and approve a transaction before it counts).

2. The transaction model: Execute‑Order‑Validate

Fabric's defining architectural choice is running these three phases in this specific order, which is not the obvious way to build a blockchain and has direct consequences for what can be measured:

client ──proposal──▶ endorsing peers   (simulate chaincode, sign RW-set)   ── T1..T2
       ◀─endorsements─
client ──envelope──▶ orderer (Raft / SmartBFT)  (batch into a block)       ── T2
                     orderer ──block──▶ all peers
                     peers: VSCC (endorsement policy) + MVCC (RW-set) + commit ── T3

Why "execute before order" is the whole point

Most simpler ledger designs order transactions first, then execute them one at a time in that order (Execute-after-Order). Fabric does the opposite: the client sends a proposal to a set of endorsing peers, each of which independently simulates the chaincode against its current world state and returns a signed read/write set — before consensus has run at all. Only after enough endorsements are collected does the client assemble an envelope and hand it to the orderer.

The practical effect: endorsement (execution) and ordering (consensus) are two genuinely separate network round-trips, each with its own, independently measurable cost. This is why Fabric can produce a real, meaningful T1→T2 number that reflects actual network and computation work — endorsement really did happen, and it really did take some measurable amount of time, before the orderer was ever involved. Compare this to Fabric-X (covered on its own page), where the equivalent round-trip is folded into one blocking call and no such split exists.

What can go wrong that a simpler model can't represent

Because execution happens speculatively, before global ordering, two transactions can validly execute against overlapping state and only conflict once ordering imposes a sequence on them. Fabric's per-peer commit phase runs an MVCC (multi-version concurrency control) check against the read set each endorser captured; if the world state moved between simulation and commit, the transaction is committed to the ledger but marked invalid. Separately, VSCC (Validation System Chaincode) enforces the endorsement policy itself — did the required set of organizations actually sign this? A transaction can fail either check independently. The harness counts either failure mode as a benchmark failure (Valid=false), even though the transaction did make it into a block; a naive tool that only checked "did it get into a block" would over-count successes.

3. Exactly how this harness measures it

The Fabric adapter (pkg/adapters/fabric) deliberately uses the Fabric Gateway SDK's fine-grained call sequence — NewProposal → Endorse → Submit → Commit.Status — instead of the SDK's convenient one-shot contract.SubmitTransaction helper. That one-shot call blocks internally until the transaction commits, which would silently merge T2 and T3 into a single number and throw away the distinction between "the orderer accepted this" and "this is now final." Using the fine-grained flow keeps them genuinely separate:

  • Writes — Endorse then Submit (T2 = orderer accept); finality is observed via Commit.StatusWithContext (T3).
  • Reads — served by Evaluate against a single peer's current state, with no ordering step at all. Finality is immediate by construction (Valid=true, T3 = now) — a read never touches the orderer, so there is nothing to wait for.
  • TxTransfer — calls Transfer(from, to, amount) on the kvstore chaincode, which does a read-modify-write of two account keys inside one simulated proposal.

The chaincode itself (chaincodes/kvstore/kvstore.go) exposes exactly three operations — Put, Get, Transfer — and is deliberately trivial, so the measured cost reflects Fabric's platform path (endorsement, ordering, validation, commit), not any complexity in the chaincode logic itself. Account balances are created lazily with a large default balance so no separate seeding phase is needed before a benchmark run.

4. The two variants: CFT and BFT

Both variants share the same adapter and the same T1/T2/T3 measurement approach — the only thing that changes is which consensus algorithm the orderer runs, which changes how many rounds of network agreement happen between T2 and T3.

VariantBranch / tagOrdererLocal topologyConsensus fault model
fabric-cftrelease-2.5, pinned v2.5.11Raft (etcd/raft)1 peer, 1 orderer, 1 CACrash-fault tolerant: survives nodes going silent, not nodes acting maliciously
fabric-bftv3.1.x, pinned v3.1.1SmartBFT1 peer, 4 orderers, 1 CAByzantine-fault tolerant: needs 3f+1 nodes (minimum 4) to survive f actively malicious nodes

main is deliberately never used for either variant — both are pinned to specific tagged releases so that a result reported today is reproducible against the same binary later, rather than silently drifting as upstream Fabric changes. SmartBFT specifically needed the v3.1.x line because it only reached production-ready status there (v3.1.4, Feb 2026); the v3.0 line that GA'd in 2024 predates that.

The practical consequence of the fault model difference: SmartBFT's minimum-4-orderer requirement means every BFT run pays for an extra round of cross-orderer agreement that Raft's single-leader design doesn't need at low contention. This shows up as ordering-phase cost between T2 and T3 — comparing CFT's and BFT's T3-based latency directly is exactly the kind of comparison this harness is built to make honestly, because both go through the identical endorse→order→validate→commit shape; only the middle step's cost differs, and that's a legitimate, meaningful thing to compare.

bash deploy/docker/fabric-cft/down.sh

Native peer/orderer Prometheus metrics are exposed at :9443/:9444 — informational only, never used in cross-platform comparison tables (see the normalization page for why).

Known gotchas

  • First up.sh run downloads roughly 1 GB of Docker images — budget time for it.
  • SmartBFT needs its full 4-orderer set even for a local run — it is the most memory-hungry Fabric variant, so local.yaml tunes per-container limits down accordingly.
  • If chaincode deployment fails, first check the chaincode module builds standalone: cd chaincodes/kvstore && go build ./... (it depends on fabric-contract-api-go/v2).

8. Why Fabric is the reference point for the other three

Fabric is the only platform in this benchmark where every stage of the T1/T2/T3 timeline maps directly onto a real, separately-observable network event with no approximation needed. That's exactly why it's useful as the baseline when reading the other platform pages: Drunix inherits this model nearly unchanged (and its one deviation — where finality has to be read from — is explained relative to this page); Fabric-X and NeuChain both diverge from it in ways that remove or reshape T2, and understanding why requires first understanding what T2 means here, where it's unambiguous.
