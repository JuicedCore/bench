Bench Overview Load path Fabric Drunix Fabric-X NeuChain Normalization

From load generator to ledger How offered TPS becomes a platform-native transaction — adapters, ports, components, and why results look the way they do.

The harness never “speaks Fabric” or “speaks NeuChain” at the top. It emits one logical Transaction. Each adapter turns that into the platform’s real API. Deploy scripts expose the endpoints; the adapter dials them; the load generator schedules when to send and when to count a commit.

Scope

Normalized kv-write / probe-sweep is the primary path. Observed numbers from campaign 20260916T065029Z-local-32gb (18 CPU / 20 GB) — illustrative, not a published ranking.

2. How load is generated and how it changes

Code: pkg/loadgen/generator.go, phases built in pkg/harness/engine.go. Methodology: docs/architecture/metrics-methodology.md.

2.1 Modes

ModeHow rate is controlledLatency clock
Open-loop (default for normalized)Absolute schedule: tx k is due at start + k/rate. The generator keeps offering even if the platform is slow.From scheduled send time (coordinated-omission safe), not from when the goroutine actually woke up.
Closed-loop (multi-client.yaml)Fixed pool of workers; each does Submit → WaitForFinality → next.scheduled == T1 (actual send).
Sweep (probe-sweep.yaml)A sequence of open-loop phases with different offered TPS.Same as open-loop per phase.

2.2 Probe-and-sweep (how load changes during a campaign)

This is the primary methodology. One YAML drives every platform with the same ladder:

  1. Probe — 10 TPS × 30 s → floor latency.
  2. Sweep steps — [100, 250, 500, 1000, 2000, 3500, 5000, 7500, 10000] TPS, 60 s each.
  3. Hold — 5 minutes at 0.9 × the highest step that actually held (not 90% of 10000).

A step “holds” only if all of these pass:

  • fail rate ≤ 2%
  • confirmed TPS ≥ 95% of offered
  • send-gap p99 ≤ 50 ms (load generator itself is not the bottleneck)

After 2 consecutive failed steps, higher rungs are skipped (abort_after_failed_steps: 2). That is how a slow platform does not burn an hour climbing a ladder it already failed.

flowchart LR
  P["probe<br/>10 TPS × 30s"] --> S1["sweep steps<br/>100 → 10k TPS"]
  S1 --> DEC{"step holds?<br/>fail≤2% · conf≥95% · gap p99≤50ms"}
  DEC -->|yes| NEXT["next step"]
  NEXT --> S1
  DEC -->|2 fails| HOLD["hold 5m<br/>at 0.9 × highest held"]
  DEC -->|pass ladder| HOLD
In-flight cap. Default ≈ max(target_tps × 8, 1024). If the platform stops finalizing, the schedule still fires; those txs are recorded as failures: “not sent: N transactions already in flight”. That is overload signal, not a bug in the generator.

Headline throughput and latency always use T3 (confirmed commits). T2 is for diagnosing where time went — and it does not mean the same thing on every platform (see NeuChain).

2.4 Keys, seed, multiple generators

  • Distributions: uniform, zipfian, fixed — seeded, identical stream on every platform for the same seed.
  • Normalized probe-sweep uses seed: 1, 200k key space, 64-byte values, finality_wait: 60s.
  • If the profile has load_gen_cpus: 2, the engine starts two generators that split rate and use seeds seed and seed+1 — same total offered TPS, different key subsequences. Changing generator count changes the key sequence, so it is a fairness lever recorded in the manifest.

3. Adapter contract

Interface: pkg/adapters/adapter.go. Every platform implements:

Setup(ctx, AdapterConfig) error
Teardown(ctx) error
Submit(ctx, *Transaction) (*SubmitResult, error)   // returns at T2 — never waits for commit
WaitForFinality(ctx, txID, timeout) (*FinalityResult, error)  // T3
Query(ctx, key) (*QueryResult, error)              // verification only
MetricsEndpoint() string                           // informational scrape only

Critical rules:

  • Submit must use the platform’s async path so T2 ≠ T3. Fabric does not use one-shot SubmitTransaction.
  • Adapters are concurrent-safe after Setup; many loadgen goroutines call them at once.
  • Adapters do not deploy networks. Endpoints come from connection.env → YAML adapter: extras.
  • Native Prometheus endpoints (peer :9443, Fabric-X :9643, …) are scraped for dashboards only. Ranking numbers come from the harness collector.

5. Normalized vs optimal (native)

Policy: ADRs 009 / 010 / 012 / 013. Short version:

  • Normalized = same YAML bytes, same seed, same ladder, same resource budget, same orderer batch params (where applicable). Goal: fair cross-platform comparison. Record caveats when a platform cannot hold a lever (e.g. Fabric-X only has Postgres).
  • Native / optimal = tune for that platform’s ceiling (CouchDB, token path, different batching, etc.). Never average with normalized numbers.
Native set is live

Per-platform files live in configs/native/ (normalized: false). Deploy honours BENCH_NORMALIZED=false: native orderer batch, native state DB, per-platform generator count. The report keeps those rows in a separate section and never ranks them against normalized numbers. Token SDK / UTXO on Fabric-X is still not implemented — that native file is kv-write over gRPC. Old REST token configs were removed with that path.

A local-32gb native kv-write probe-sweep is scripts/run-all.sh configs/native …. Native kv-mixed (same levers, 50% reads) is configs/native-kv-mixed. The last normalized campaign was a different directory under results/_campaigns/.

6. fabric-cft — Fabric Raft + chaincode

normalized: LevelDB held EOV + chaincode Gateway gRPC Fabric 2.5.x

Topology (local-32gb)

Budget split across 5 containers: 2 peers, 1 Raft orderer, 2 chaincode containers. Profile: 18 CPU / 20 GB total.

How the endpoint is exposed

  1. deploy/docker/fabric-cft/up.sh bootstraps fabric-samples test-network, installs kvstore on channel mychannel.
  2. Writes deploy/docker/fabric-cft/connection.env with peer TLS material and:

Chaincode (chaincodes/kvstore):

Put(ctx, key, value) → stub.PutState(key, []byte(value))

Blind write: no read-set → almost no MVCC conflicts on kv-write. World state stores the raw 64 bytes.

Other tx kinds

  • kv-read → Gateway Evaluate("Get") on one peer. No orderer, no commit. Finality is immediate. Not comparable to NeuChain reads.
  • transfer → chaincode Transfer: real balance RMW on acct/… keys with JSON balances. Hot Zipfian keys → real MVCC_READ_CONFLICT.

Normalized or optimal?

Both exist. Normalized uses LevelDB + the shared 100 / 1s batch. Native (configs/native/fabric-cft.yaml) keeps LevelDB but cuts blocks at 500 msgs / 500ms.

Why it behaves this way

Endorsement RTT + Raft batching + validation dominate. At low TPS, latency often falls as blocks fill faster (batch timeout 1 s). Past the knee, in-flight backlog explodes e2e p99 while confirmed TPS plateaus.

Observed (local-32gb probe-sweep): saturation ~2000 offered; hold@1800 → confirmed ~1545 TPS, fail_rate ~0.14, e2e p99 ~30 s — hold ran past a soft knee, so headline TPS is usable but latency is not “clean.”

7. fabric-bft — Fabric SmartBFT + same chaincode

normalized: LevelDB held EOV + chaincode Gateway gRPC Fabric 3.1.x · 4 orderers

Same adapter package as CFT (pkg/adapters/fabric), same kvstore chaincode, same client-facing port :7051. Difference is consensus: SmartBFT needs 4 orderers (3f+1). Deploy uses fabric-samples BFT profile. Mutually exclusive with CFT on the same host (shared ports).

flowchart LR
  CLI["Client / adapter"] --> GW["Gateway peer :7051<br/>same Put path as CFT"]
  GW --> O1["SmartBFT<br/>4 orderers"]
  O1 --> PE["Peers<br/>VSCC + MVCC + LevelDB"]
  PE --> T3["Block events → T3"]

Normalized or optimal?

Normalized API and batch levers match CFT. Native (configs/native/fabric-bft.yaml) keeps kv-write on LevelDB but uses a BFT-specific batch (250 msgs / 1s). BFT is still heavier (4 orderers); the same 20 GB budget is split thinner than CFT.

Why it behaved poorly on local-32gb

Same 20 GB budget is split across 8 containers (2 peers + 4 orderers + 2 CC). Peers get ~4.5 GB each vs ~6.8 GB on CFT. Under sweep load the gateway peer hit its cgroup limit and was OOM-killed (exit 137) — run excluded, no headline. This is a resource-split failure, not evidence that SmartBFT “can’t do TPS.”

Why JSON wrap? Drunix’s Yugabyte statedb writer force-casts values to JSONB and panics on raw strings. The wrap is client-side only (pkg/adapters/drunix/valuecodec.go), disclosed as a caveat. Transfers already produce JSON balances and are not re-wrapped.

Normalized or optimal?

Both exist. Normalized is kv-write with LevelDB requested (actual Yugabyte — “PARITY NOT HELD”) and the shared batch. Native (configs/native/drunix.yaml) is the same kv-write Put on Yugabyte with 500 msgs / 500ms — disaggregated peer + SQL state, not a transfer/RMW run.

Why TPS is lower than fabric-cft

More containers → less CPU/mem per node; extra hop Lite Peer → Committing Peer; Yugabyte write path; slightly larger on-wire values. Observed: knee ~500 offered; hold@450 → 450 confirmed TPS, clean fail_rate 0, e2e p50/p99 ~538/762 ms.

No chaincode. Input bytes are stored bytes. Blind write ⇒ no MVCC on old version.

Why all four routers? Sending to a single non-primary router adds ~10 s FirstStrike delay. Broadcasting avoids that path. Old connection.env files with only :6022 produce invalid latency numbers.

Other tx kinds

  • kv-read → GetRows on :7001. No order/commit. Same “not a ledger tx” shape as Fabric Evaluate.
  • transfer → two-key read/write set with empty values (contention shape only; no balance arithmetic). Not optimal Fabric-style transfer.

Normalized or optimal?

Normalized is the kv-write cell with the shared batch and Postgres (parity not held). Native (configs/native/fabricx.yaml) is still kv-write over gRPC — Token SDK UTXO is not implemented — but requests Postgres, uses Arma 500 / 500ms, and 512 broadcast streams.

Why it is fastest on this host

No peer endorsement RTT for chaincode; sharded Arma path; four fat containers get more CPU each than Fabric’s many small ones. Observed: held through 7500; failed 10000; hold@6750 → 6750 confirmed TPS, fail_rate 0, e2e p50/p99 ~524/737 ms.

10. neuchain — ZMQ Execute-Validate

ordering-free EV ZMQ + protobuf + RSA-1024 YCSB payloads

Topology

Typically 4 block-server-* containers (block + epoch co-located), Docker network 172.30.7.0/24.

RoleHost portsComponent

T2 is not comparable. On NeuChain, T2 is “bytes left the client socket.” Do not use submit latency to compare NeuChain to Fabric/Fabric-X. Use e2e (T3) and confirmed TPS only.

Other tx kinds

  • kv-read → a committed read-carrying transaction (full path), not a point query. Different semantics from Fabric Evaluate / Fabric-X GetRows.
  • transfer → rejected at Submit (not implemented).

Normalized or optimal?

Same logical kv-write cell. Native (configs/native/neuchain.yaml) shortens sweep steps and hold so the run can finish before the upstream epoch-10000 crash. It is still YCSB over ZMQ — not a different chaincode.

Why the last campaign failed

Deploy appeared to start, but adapter setup could not complete ZMTP greeting to localhost:5001 (connection reset by peer). No saturation numbers from that campaign. Historically, NeuChain also has a known upstream segfault around epoch 10 000 on long runs — separate from this connection failure.
